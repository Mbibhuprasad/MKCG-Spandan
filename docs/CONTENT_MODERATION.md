# Content moderation

Code: `backend/src/models/plugins/moderation.js`, `backend/src/services/content.service.js`,
`backend/src/services/moderation.service.js`, `backend/src/controllers/admin.controller.js`.

Content moderation status is entirely separate from **account** status. Registering and logging in never require
approval; publishing content does.

## What is moderated

| Type | Model | Owner field | Likes | Comments |
| --- | --- | --- | --- | --- |
| Post | `Post` | `author` | Yes | Yes |
| Blog | `Blog` | `author` | Yes | Yes |
| Comment | `Comment` | `author` | — | — |
| Memory (photos / videos) | `Memory` | `owner` | Yes | Yes |
| Event and visit plan | `Event` (`eventType: VISIT_PLAN` for visit plans) | `organizer` | — | Yes |
| Poll | `Poll` | `creator` | — | — |

## Statuses

| Status | Meaning | Who can see the item |
| --- | --- | --- |
| `PENDING` | Submitted, awaiting review | The owner and administrators |
| `APPROVED` | Published | Members (and, for blogs, the public) |
| `REJECTED` | Reviewed and not published | The owner (with the reason) and administrators |

Every moderated document also stores `submittedAt`, `reviewedAt`, `reviewedBy`, `rejectionReason` and `publishedAt`.

## Lifecycle

```
doctor creates ──▶ PENDING ──approve──▶ APPROVED ──(doctor edits)──▶ PENDING …
                      │                    │
                      └──reject──▶ REJECTED ──(doctor edits)──▶ PENDING …
admin creates ──▶ APPROVED (published immediately)
any state ──(owner deletes, or admin deletes)──▶ removed with its dependants
```

1. **Create.** The handler validates text and media, sets the owner from the session and calls
   `initialModeration(user)`: `PENDING` for a doctor, `APPROVED` (with `reviewedAt`, `reviewedBy`, `publishedAt`) for
   an admin. No request field can influence this.
2. **Author feedback.** The response includes `moderation.status`, and the item appears under
   `GET /<type>/mine` and on the dashboard (`/dashboard/submissions`) with its status.
3. **Review.** The item appears in the matching admin queue. `PATCH /admin/moderation/:queue/:id` with
   `action: approve | reject` (and an optional `reason`) calls `moderation.review()`.
4. **Publication.** Approved items appear in the relevant feed, directory or gallery. `publishedAt` is set the first
   time an item is approved and is used for ordering.
5. **Rejection.** The item stays hidden from everyone but its owner and admins. The owner sees the reason and may edit
   and resubmit.
6. **Editing.** When a doctor edits their own item, `resetModerationAfterEdit()` returns it to `PENDING` and clears the
   previous review. Otherwise an approved item could be changed into something that was never reviewed. (Editing by
   an admin of their own content does not reset it.)
7. **Deletion.** The owner can delete their own item at any time. An admin can delete **any** item in any state,
   including approved content, through `DELETE /admin/moderation/:queue/:id`.

### Polls

A poll can be edited only while it is not approved and has no votes (`409 POLL_LOCKED` otherwise), so the options
people voted on can never change. To change a published poll, delete it and create a new one.

## Visibility rules (enforced by the API)

| Request | Result |
| --- | --- |
| Feed / list endpoints (`GET /posts`, `/blogs`, `/memories`, `/events`, `/polls`) | Filter `moderationStatus: APPROVED` for every caller |
| `GET /<type>/mine` | The caller's own items in all states |
| Single item (`GET /posts/:id`, `/blogs/slug/:slug`, …) | Approved → visible; otherwise only for the owner or an admin; everyone else gets `404` (indistinguishable from a missing item) |
| Comment thread (`GET /comments`) | Approved comments plus the caller's own pending/rejected comments |
| Like, comment, report, RSVP, vote | Only on approved targets (`409 NOT_PUBLISHED` for the owner previewing their own pending item) |
| Edit / delete of someone else's item | `404` if it is unpublished, `403` if it is published |
| A memory linked to an unpublished event | The event title is shown only to the memory's owner and admins |
| Public pages | Only approved blogs, opted-in featured doctors and opted-in event summaries |

Because the status is never accepted from the client and only `moderation.service.js` (reached exclusively through
`/admin` routes guarded by `requireAdmin`) can change it, a doctor cannot approve their own submission by calling the
API directly.

## Comments

- A doctor's comment starts `PENDING`; an admin's comment is published immediately.
- Each commentable item keeps `commentCount` = number of **approved** comments. It is adjusted when a comment is
  approved, un-approved (rejected after approval, or edited by its author), or deleted while approved.

## Notifications generated by moderation

| Event | Recipient | Type |
| --- | --- | --- |
| Item approved | Owner | `CONTENT_APPROVED` (link to the item) |
| Item rejected | Owner | `CONTENT_REJECTED` (reason, link to submissions) |
| Item deleted by an admin | Owner | `CONTENT_REMOVED` |
| Event or visit plan approved | All active doctors except the organiser | `EVENT_PUBLISHED` |
| Poll approved | All active doctors except the creator | `POLL_PUBLISHED` |
| Comment approved | Owner of the item that was commented on (if different from the commenter) | `NEW_COMMENT` |

Fan-out and comment notifications carry a dedupe key, so re-approving an item does not notify twice. Reviewing an item
that is already in the requested state is a no-op.

## Admin queues

`GET /admin/moderation/:queue?status=PENDING|APPROVED|REJECTED|ALL`

| Queue | Contents |
| --- | --- |
| `posts` | Posts |
| `blogs` | Blogs (with the rendered body) |
| `comments` | Comments, each with a summary and link of the item it belongs to |
| `memories` | Memories with their media |
| `events` | Events except visit plans |
| `visit-plans` | Events with `eventType: VISIT_PLAN` |
| `polls` | Polls |

Pending queues are ordered oldest-first so submissions are handled fairly; other views are newest-first. Each item
shows its submission and review timestamps. The admin dashboard (`GET /admin/stats`) shows the pending count for
every queue. An item can only be acted on through the queue it belongs to (an event id is not accepted in the
`visit-plans` queue and vice versa).

Review uses a compare-and-set on the previous status; if two admins act at once, the second receives `409 CONFLICT`
and should refresh.

## Reports

Members can report a post, blog, comment, memory, event or poll (`POST /reports`) with a reason and optional details —
once per item, and not their own content. Admins see reports at `GET /admin/reports` together with the current state
of the reported item and the queue where it can be reviewed, then mark each report `RESOLVED` or `DISMISSED`.
Reports about an item are deleted with the item.

## Audit trail

Approvals, rejections and admin deletions are written to the audit log (`CONTENT_APPROVED`, `CONTENT_REJECTED`,
`CONTENT_DELETED`) with the admin, the item id, its owner and the reason.

## Account sanctions

For repeated or serious violations an admin can suspend the doctor (every request is refused at once, no login) or delete the
account together with all of its content. Both actions notify/are logged as described in
[ROLES_AND_PERMISSIONS.md](ROLES_AND_PERMISSIONS.md) and [DATABASE.md](DATABASE.md).

## Remaining limitations

- Moderation is manual; there is no automated screening of text, images or videos.
- Suspending a doctor does not unpublish content they already published — reject or delete it separately.
- There is no bulk approve/reject and no edit-by-admin; admins approve, reject or delete.
- Notifications are in-app only (no email or SMS).
- Previous versions of edited content are not kept.
